# ADR 0004: Authentication — hybrid JWT, dual-ID identity, one storage pattern

- **Status:** Accepted
- **Date:** 2026-05-21
- **Deciders:** John O'Conner
- **Supersedes / supersedes-by:** —

## Context

The bar-trivia server authenticates four kinds of identity (per [docs/requirements.md §3](requirements.md) and [CLAUDE.md](../CLAUDE.md)):

- **Guests** — players who join a room by code with a generated display name, no signup. Must be frictionless (the friction case for guest play is load-bearing per [docs/requirements.md "Resolved"](requirements.md#resolved)). Identity must survive a reconnect mid-game with score intact (per [§6.1](requirements.md#61-player-disconnect)).
- **Registered players** (v2) — email/password accounts; persistent stats and lifelines. Schema-aware now even if features are deferred.
- **Hosts** — full accounts always; own packs and game history.
- **Admins** — operational role; not yet defined.

The auth layer touches three trust boundaries:

1. **REST** — login, refresh, account management, room creation, etc.
2. **Socket.IO handshake** — authenticated WebSocket connections need to attach identity to each socket.
3. **Persistent storage** — passwords, refresh tokens, session metadata.

Constraints from prior ADRs:

- [ADR 0001](0001-server-stack.md) locks NestJS on Express v5 and Zod for validation. Auth schemas live in `packages/shared`.
- [ADR 0002](0002-database.md) locks Postgres + Prisma. No Redis yet; live in-process state for rooms.

Constraint from competitive-landscape survey:

- [docs/competitive-landscape.md](competitive-landscape.md) flagged TriviaForge's **dual-ID session model** (per-device PlayerID + per-room RoomSessionID) as the most-cited reliability feature for bar-Wi-Fi reconnection. Worth borrowing.

This ADR makes five decisions: session mechanism, refresh token storage, client-side token storage, guest identity model, and password hashing.

## Decisions

### 1. Session mechanism: hybrid (short JWT access + server-stored refresh)

Access tokens are **JWTs, 15 minutes**, signed with a server secret. Refresh tokens are **opaque random strings, 7 days**, stored hashed in Postgres and rotated on every refresh.

Rationale:

- Pure stateless JWT (no refresh tokens) has no real revocation path. Revoking a single token requires rotating the signing key, which logs every active user out. Unacceptable for a product where a host might need to be removed from a venue, or where a stolen device needs to be killed.
- Pure server sessions (cookie → session ID → DB lookup) work but require a session lookup on every request — including every Socket.IO event. They also don't naturally scale across multiple server instances without a shared store.
- The hybrid pattern is the de facto standard for SPA + API + WebSocket apps: stateless scale during normal operation, real revocation during exceptional operation. The 15-minute access-token lifetime keeps the "can't revoke a JWT mid-flight" blast radius small.

The Socket.IO handshake passes the access token via `auth: { token }`; the gateway verifies on connection and attaches identity to `SocketData`.

### 2. Refresh tokens are stored in Postgres, hashed, per-device

A `refresh_tokens` table holds one row per active refresh token. Schema sketch:

```prisma
model RefreshToken {
  id            String   @id @default(uuid())
  userId        String
  user          User     @relation(fields: [userId], references: [id])
  tokenHash     String   @unique  // SHA-256 of the raw token; raw never stored
  deviceLabel   String?            // optional human label ("iPhone 14", "Chrome on Mac")
  createdAt     DateTime @default(now())
  lastUsedAt    DateTime?
  expiresAt     DateTime
  revokedAt     DateTime?
  rotatedToId   String?  @unique   // if rotated, points at the replacement row
}
```

Rationale:

- The token's raw form is sent to the client once and never stored server-side — the row holds only the SHA-256. A leaked database dump cannot impersonate users.
- One row per device enables a future "list / revoke my sessions" UI without schema change.
- Rotation creates a new row and marks the old one's `rotatedToId`. If a client ever presents a rotated-but-not-revoked token, that's **token reuse detection** — revoke the entire chain (someone else has the token). This is a well-documented mitigation for stolen refresh tokens.
- Postgres rather than Redis because no Redis exists yet (per [ADR 0002](0002-database.md)) and the write rate (one row updated every ~15 min per active user) is not a Postgres scale concern at the planned bar count.

### 3. Client storage: one pattern for all roles

**All users — guest, player, host, admin — use the same storage pattern:**

- Access token (15min) lives in **JavaScript memory** only. Lost on page refresh; refilled via a silent refresh call.
- Refresh token (7d) lives in a **httpOnly, Secure, SameSite=Lax cookie**, path-scoped to `/auth/refresh`. Unreadable by JavaScript — survives XSS, supply-chain attacks, browser-extension snooping.

Rationale:

- The httpOnly-cookie pattern is the standard answer for SPAs that take XSS seriously. The implementation cost is ~30 lines of one-time plumbing (set cookie on login/refresh, send `credentials: 'include'` on refresh fetches, keep an in-memory token in a small fetch wrapper). That cost is paid once and never revisited.
- Treating guests differently was considered (localStorage for both tokens, no refresh cookie) on the grounds that guest tokens have a smaller blast radius. Rejected because it doubles the auth code path for marginal gain. The httpOnly-cookie protection is also genuinely valuable for guests — a stolen guest token can be invalidated server-side via the refresh-token table, which localStorage-only design cannot do.
- The "access token in memory + refresh in cookie" pair is what makes page reload survive without re-login: memory is wiped on reload, the refresh cookie is sent automatically to `/auth/refresh`, server mints a new access token, user never notices. Guests get the same UX (mid-game reconnect on a flaky bar Wi-Fi reload is a common case, per [§6.1](requirements.md#61-player-disconnect)).
- One code path across all roles. One token table. One refresh flow. No special cases.

### 4. Guest identity: `users` table with `role=guest` + dual-ID reconnection

Guests are stored in the same `users` table as registered users, with nullable `email` and `passwordHash` columns and `role='guest'`.

```prisma
enum UserRole { guest player host admin }

model User {
  id            String   @id @default(uuid())
  role          UserRole
  displayName   String
  email         String?  @unique     // null for guests
  passwordHash  String?              // null for guests; argon2id for others
  createdAt     DateTime @default(now())
  // ... refresh tokens, participations, etc.
}
```

The dual-ID reconnection pattern (from [docs/competitive-landscape.md](competitive-landscape.md), originating with TriviaForge) is preserved via a separate `room_participants` table that holds the per-room session ID:

```prisma
model RoomParticipant {
  id              String   @id @default(uuid())  // the RoomSessionID
  userId          String                         // the PlayerID (stable per device)
  user            User     @relation(fields: [userId], references: [id])
  roomCode        String
  displayName     String                         // captured at join time
  joinedAt        DateTime @default(now())
  lastSeenAt      DateTime @default(now())
  // score, response times, etc.
}
```

The access-token JWT carries both `sub` (the user.id, durable PlayerID) and `roomParticipantId` (the per-room RoomSessionID). Reconnect logic uses the RoomSessionID to restore the specific in-room state (score, answered questions); the PlayerID identifies the player across rooms and across the eventual guest→registered upgrade path.

Rationale:

- One identity table, one auth code path. Same Prisma model whether the user is a guest, player, host, or admin.
- Guest→registered upgrade is a single `UPDATE users SET email=?, passwordHash=?, role='player' WHERE id=?` — no row migration, no data copy, no foreign-key thrash. Everything the guest did (`RoomParticipant` rows, future stats) already points at the right user ID.
- Nullable `email`/`passwordHash` are mildly ugly but truthful — a guest genuinely doesn't have those.
- The dual-ID separation (durable identity vs per-room session) is preserved cleanly without a parallel `guest_sessions` table. The per-room state lives on `RoomParticipant`, which is data you'd model regardless.
- Guest retention: guests with `lastSeenAt` older than N days can be swept (and their `RoomParticipant` rows cascade). Retention policy is a deferred decision; the schema doesn't lock it.

### 5. Password hashing: argon2id via `@node-rs/argon2`

Use **argon2id**, OWASP's recommended algorithm since 2021, via the `@node-rs/argon2` package (Rust native binding).

Sensible defaults: ~64MB memory cost, ~3 iterations, parallelism 1. Tune up if benchmarks on the deploy target show headroom.

Rationale:

- argon2id won the Password Hashing Competition and is the current recommendation. bcrypt is fine but legacy; scrypt is fine but less commonly chosen. There's no scenario in 2026 where a new project should pick bcrypt over argon2id unless a deployment constraint forbids native modules.
- `@node-rs/argon2` is a Rust binding via napi-rs — faster than the pure-JS implementations and avoids node-gyp build pain that plagues the older `bcrypt` npm package.

## Consequences

Positive:

- One identity table, one JWT shape, one auth middleware across guest / player / host / admin.
- Stateless scale during normal operation; real revocation when needed.
- Reconnection-with-score-intact (required by [§6.1](requirements.md#61-player-disconnect)) is a property of the schema, not a special case.
- Guest→registered upgrade is a trivial column update.
- Token leak via XSS is bounded for everyone: access tokens have a 15-minute lifetime, refresh tokens are httpOnly and unreadable by JavaScript.
- argon2id meets current OWASP guidance with no decision to revisit.

Negative:

- The hybrid scheme is more moving parts than pure JWT or pure sessions. Worth it; not free.
- The httpOnly-cookie pattern requires `credentials: 'include'` discipline on the refresh fetch and a CORS configuration that allows credentials. Standard but easy to misconfigure.
- Refresh token rotation logic must handle race conditions (two simultaneous tabs both trying to refresh). The standard solution — token-reuse detection revokes the chain — handles this; document it in the implementation.
- The `users` table has nullable `email` and `passwordHash`. Querying registered-only users requires `WHERE role != 'guest'` (or a partial unique index on email). Acceptable.
- Cookies are sent on every request to the cookie path. Limiting the refresh cookie to `path=/auth/refresh` keeps it off normal API calls and Socket.IO upgrades.

## Alternatives considered

### Stateless JWT only (no refresh tokens)

Rejected. No revocation path short of rotating the signing key. Cannot kill a stolen device, a removed host, or a compromised account. Standard "JWT considered harmful" critique applies precisely here.

### Server sessions only

Rejected. Requires session lookup on every request including every Socket.IO event. Doesn't naturally work across multiple server instances without a shared store (which would mean adding Redis just for sessions — premature per [ADR 0002](0002-database.md)). Cross-origin friction if TV/API are on different subdomains.

### Redis-backed refresh tokens

Rejected. Premature. Adding Redis just for refresh tokens, before the multi-server pressure that [ADR 0002](0002-database.md) earmarks Redis for, is over-engineering. Postgres handles the write rate trivially at planned scale.

### Separate `guest_sessions` table

Considered and rejected. The cleaner-on-paper separation creates two parallel identity tables, two auth code paths, and a real data migration on guest→registered upgrade. The "users table with role=guest and nullable account columns" pattern is uglier in the schema but materially simpler everywhere else.

### Everything in localStorage (no httpOnly cookie at all)

Considered. Simpler — no cookie infrastructure. Rejected because the refresh token would then be XSS-readable, defeating the main reason to have a short-lived access token in the first place. Also, the migration cost later (forced re-auth, client rewrite) is real.

### Split by trust tier: localStorage for guests, cookie+memory for registered

Considered. The original draft of this ADR proposed exactly this. Rejected on reflection because the cost of supporting guests through the same flow is essentially zero (same endpoints, same cookie logic), and the benefit is real: a stolen guest token can be invalidated server-side, which localStorage-only cannot do. The "guests are lower investment so let them have weaker protection" framing was an unnecessary special case.

### Cookies for everything (access token in cookie too)

Considered. Maximum defense-in-depth. Rejected because access tokens then attach to every API request and Socket.IO upgrade — Socket.IO `auth: { token }` is cleaner than parsing cookies on the WS handshake, and `Authorization: Bearer` is the well-trodden REST path. Cookies on every request also expand CSRF surface unnecessarily for the access token (which is already short-lived).

### bcrypt for password hashing

Considered. Fine. Rejected because argon2id is OWASP's current recommendation and there's no constraint in this project that argues against native modules.

## Invariants this ADR establishes

These are load-bearing rules for future work:

- **One JWT shape for all roles.** Access tokens carry `{ sub: userId, role, displayName, roomCode?, roomParticipantId? }` and are verified the same way regardless of role. Guards differentiate by `role`, not by token type.
- **Refresh tokens never appear in any log, response body, URL, or non-cookie storage.** Raw refresh tokens transit on the wire in a `Set-Cookie` header exactly once per rotation; the server stores only the SHA-256.
- **Rotation on every refresh.** Every successful `/auth/refresh` call mints a new refresh token and marks the old one rotated. Presenting a rotated-but-not-revoked token revokes the whole chain.
- **Identity is one `users` table.** No parallel guest table. Adding a second identity table requires its own ADR.
- **Dual-ID reconnection** is implemented via `RoomParticipant.id` (RoomSessionID) and `User.id` (PlayerID). The JWT carries both; reconnect logic uses RoomSessionID to restore in-room state.
- **Password hashing is argon2id.** Switching algorithms requires its own ADR and a rehash-on-next-login migration path.
- **Client storage is one pattern for everyone.** Access token in JS memory, refresh token in httpOnly Secure SameSite=Lax cookie scoped to `/auth/refresh`. No role-specific exceptions. Changing this requires its own ADR.

## Deferred (intentionally)

- **OAuth / Google login.** Schema is compatible — a future `oauth_identities` table joins to `users.id` without changing the auth flow described here. Picking the provider, registering the app, callback URL handling — all deferred per existing CLAUDE.md note.
- **MFA / 2FA.** Not MVP. Add when there's an account-level reason to (e.g., host accounts unlock paid features).
- **Guest retention sweep policy.** How long do `role='guest'` rows live after `lastSeenAt`? Add when storage volume justifies the answer.
- **Admin role specifics.** ADR establishes the enum value; what admin can actually do is product-side and deferred.
- **Rate limiting on `/auth/login` and `/auth/refresh`.** Listed in [docs/requirements.md §10.3](requirements.md) as a should-resolve-before-launch concern. The ADR doesn't pick a mechanism (express-rate-limit, NestJS @Throttle, fastify-rate-limit) — just records that auth endpoints need it.
